Come implementarla

Oggi l'identità è simulata con role/client nei query param. Per la visibilità per assegnazione serve un vero contesto utente.

Modello dati

  • UserAccount: id, nome, email, ruolo (Manager, PMO, Pentester, Auditor), attivo, EntraObjectId opzionale.
  • ClientAssignment: userId + clientId + data inizio/fine. Assegna tutti gli engagement del cliente.
  • EngagementAssignment: userId + engagementId + ruolo + allocazione + date. Assegna un singolo engagement.
  • ClientAccount.Users resta per gli utenti cliente, collegati al cliente; possono avere assegnazioni per singolo engagement.
  • Il Manager non ha assegnazioni: il suo ruolo implica visibilità globale.

API e filtro obbligatorio

  • GET /api/users (Manager) · GET /api/users/{id}/assignments · POST/DELETE /api/users/{id}/assignments.
  • GET /api/engagements, /api/clients, /api/dashboard/todo e ogni dettaglio devono usare AccessScope(user).
  • AccessScope: Manager → All; altri → unione client assegnati + engagement assegnati.
  • Un accesso non autorizzato restituisce 404 (non 403), per non rivelare l'esistenza dei dati.
  • Demo: sostituire il selettore “Profilo” con un selettore “Utente demo” (almeno 2 pentester, 1 PMO, 1 Manager, 1 Auditor, 2 utenti cliente).

Rollout consigliato

  • 1. Directory + assegnazioni: seed utenti, sezione Utenti, filtro API per Manager/PMO/Pentester/Auditor.
  • 2. Utenti cliente: visibilità sui propri engagement, invito e gestione.
  • 3. Vista per cliente e bulk matrix: produttività per PMO/Manager.
  • 4. Entra ID: sostituire il selettore demo con l'identità reale e i gruppi; niente role/client nei query param.
